# Releasing

AVID Core is a source library. GitHub Releases are the canonical source release record. Stable releases use a `vMAJOR.MINOR.PATCH` tag matching `Cargo.toml`; cryptographic tag signing and manual release approval are not required. Do not invent or silently change versions.

The [source release workflow](../.github/workflows/source-release.yml) is triggered by version tags. It verifies the tag/version identity, builds and tests the package, produces the CycloneDX SBOM and checksums, and publishes only after the artifact passes those checks. GitHub build provenance is best-effort and does not block publication. Failed functional or integrity checks still prevent publication of that source artifact, but do not block unrelated development or other platforms.

The [Core runtime workflow](../.github/workflows/runtime-release.yml) is a separate authenticated update path. It currently publishes one complete six-target runtime manifest; each platform's native artifact is independently built and validated, but publication remains tied to the complete manifest, checksums and GitHub attestation consumed by existing clients. Do not publish a partial runtime or bypass these integrity checks without first changing and validating all consumers. Existing release identities and assets are not overwritten.

Direct downloads use the separate [per-platform workflow](../.github/workflows/ffmpeg-independent.yml). Each target builds and runs its own native, media, lifecycle, repeatability, source-provenance, and archive checks with a read-only token. Its publisher has only Actions read and contents write access. After that target passes, it rechecks the exact Actions archive, package, corresponding sources, checksums, and target architecture, then publishes one immutable GitHub Release named `platform-ffmpeg-VERSION-rRECIPE-TARGET-runRUN_ID`. Other targets may still be queued or failed. Each release contains the runtime archive, corresponding source archive, checksums, and `platform-release.json` identifying the original run and artifact. The release tag points to the publication revision on main, while the embedded provenance and source archive identify the exact build revision. Repeating publication verifies existing bytes and metadata; it never replaces an asset. Relevant main-branch changes start new target builds automatically. No distribution signing or notarization is required for these direct downloads.

These platform releases are **not** authenticated runtime updates. ATIV and EnCAP remain pinned to `ffmpeg-9.0.1-r7.1` and its six-target manifest, digest, archive hashes, and GitHub attestation. A new platform release never changes that release or its signed update verification. The legacy [candidate workflow](../.github/workflows/ffmpeg.yml) remains available for existing qualification plans; `publish-existing-platforms.yml` can publish an already verified target from a specified candidate run without rebuilding it.

Core's native checks qualify the runtime pair for its target. They do not qualify an application. No ATIV or EnCAP build, integration test, approval, signing result, or release schedule is an input to either Core publication channel. Consumers can continue using the pinned authenticated release without waiting for a new Core build. To consume a newer platform release through an authenticated update path, they first need the separate contract described in [the provider contract](ffmpeg/provider-contract.md); direct-download checksums alone do not replace the existing attestation and manifest pin.

For either channel, keep versioning and release notes accurate, update [CHANGELOG.md](../CHANGELOG.md) where appropriate, and maintain dependency/license records when they change. See [TESTING.md](TESTING.md) and [CODE_SIGNING_POLICY.md](../CODE_SIGNING_POLICY.md) for the nonblocking development and provenance policies.
