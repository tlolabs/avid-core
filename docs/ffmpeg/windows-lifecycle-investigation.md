# Windows runtime lifecycle investigation

Resumed from `8d8a108530db85c999aac21e4e54c9b7ab0c96e2`. Recipe 7 compiler flags and release gates remain unchanged. No cause is assigned to the external process solely from the previous Restart Manager snapshot.

## Source audit before new instrumentation

- All production FFmpeg/FFprobe invocations funnel through `src/process.rs::run`. No production code sets the working directory to the runtime. Child stdin is null; stdout/stderr are piped and drained by two threads.
- Normal completion uses `try_wait`; cancellation and timeout call `kill` then `wait`. The normal return path joins both reader threads. `OwnedChild::drop` also attempts kill/wait, then Rust drops the child process object and its OS handle. Kill errors are ignored, and wait errors on interruption are currently folded into the operation error; diagnostics must establish whether these occur in the failing scenario.
- An independently identified edge case needs attention: if joining the stderr reader returns an I/O error, `?` returns before the stdout thread is joined. Dropping its JoinHandle detaches it. A panicking EventSink callback can likewise bypass explicit joins. This is not yet connected to the observed rename failure, which has not reported either condition.
- `MediaTools` stores only executable paths and version strings. `Renderer` stores MediaTools and timeout settings. Neither owns an executable file, process, memory mapping, directory handle, background worker or current-directory reference. Keeping a Renderer value in scope is therefore not itself evidence of an open executable.
- Managed manifest reads use `std::fs::read`, whose file handle closes before returning. Capability discovery uses the same synchronous process runner. Staging uses synchronous `fs::copy` and `fs::read`; their temporary handles do not escape.
- `StagedOutput` owns an output NamedTempFile under the test root, outside the runtime directory. Its successful publication returns after the persisted file and extra sync handle drop; failure/cancellation drops the temporary file. `same_file` comparisons use temporary handles outside the runtime.
- The qualification application's direct fixture/probe invocations use `Command::output`, which waits and captures both streams. These calls are outside Core and require explicit diagnostic coverage too.
- The test replaces the runtime after completed render, publication cancellation, zero-duration render timeout and staged-update discovery. The zero timeout can terminate a child during loader startup; this is a useful case that must remain covered.

## Application replacement contract

A host must stop scheduling work against the old runtime, cancel or finish active work, join its own operation threads, and then release its Renderer/MediaTools references before replacement. Core operations are synchronous and immutable Renderer clones can be called concurrently; Core has no global operation registry capable of stopping host-owned threads. The current test exercises completed synchronous operations but keeps the Renderer value alive, which is a stronger expectation for today's path-only structure. It does not yet explicitly exercise cancellation of an actively encoding native Windows child from a host worker thread. Additional coverage should supplement, not replace, the existing immediate rename/rollback/removal checks.

## Established cause and corrective behavior

The sanitized [evidence](evidence/windows-runtime-lock-r7.json) covers independent clean Windows Server 2025 x64 runners. Initial instrumented failures occurred at cycles 10, 41 and 76. All 35 children involved before the failing rename had been waited, their output readers joined, and their Core/process objects dropped; the qualification process's current directory was outside the runtime. Independent C experiments also reproduced directory rename denial without Core, while 600-cycle controls normally passed even with exited child process/thread handles retained. Retaining an exited child process object is therefore not the demonstrated cause.

Immediate in-process file-owner queries identified `provjobd.exe` (with runner-generated numeric suffixes) holding **the exact installed FFmpeg or FFprobe file**. File-ID-matched handle inspection found access mask `1179785` (`0x120089`, read data/attributes/extended attributes, read-control and synchronize), with inheritance disabled. Observed file positions included 20,700,457 of 28,502,016 bytes for FFprobe and 27,626,596 of 28,682,752 bytes for FFmpeg. These are active ordinary reads of the executable image, not leaked Core pipes or inherited handles. Ownership disappeared in subsequent samples at 114,377–233,616 microseconds after the failed operation in the measured cases. These are bounds on the observed remaining lock lifetime, not exact complete open durations. Diagnostic duplication can briefly extend the measured ownership; the earlier non-duplicating observations also showed release at 185,324 and 215,284 microseconds.

`provjobd` is GitHub runner diagnostic infrastructure: [StepSecurity's first-hand investigation](https://www.stepsecurity.io/blog/harden-runner-detects-anomalous-traffic-to-api-ipify-org-across-multiple-customers) records GitHub Support identifying its diagnostic role. Here, the directly established activity is asynchronously reading the executable. The daemon's internal metric or reason for selecting an image is not publicly documented and has not been inferred as a proven antivirus scan or a particular hash algorithm. No daemon, antivirus or monitoring service was disabled or terminated.

Windows [directory rename rules](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) disallow moving a directory while descendants have open file handles. Core cannot force an unrelated reader to close. The correct host operation therefore needs a bounded opportunity for normal asynchronous external reads to finish, after Core work itself has fully stopped. This evidence is the basis for bounded retry; no initial sleep, unconditional success, copy/delete rename fallback or failed-test retry was introduced.

The additive `move_runtime_directory` and `remove_runtime_directory` APIs attempt immediately and retry only Windows OS errors 5, 32 and 33 within an explicit caller-supplied wait budget. Zero duration preserves a single attempt; all other errors fail immediately; a persistent lock returns an error. The qualification caller uses two seconds, comfortably beyond observed sub-second external reads. Moving remains a filesystem rename. Removal can be partial on failure, as with ordinary `remove_dir_all`, so it is only appropriate for an obsolete copy outside the active/rollback paths. Other operating systems perform one ordinary filesystem operation.

The existing native test now exercises these actual host-facing runtime operations, preserving every render, publication-cancel, zero-timeout, integrity, replacement, rollback and cleanup assertion. The added native cancellation test starts real encoding on a host worker thread, cancels after progress, joins the worker, and then moves/removes the runtime. A separate-process Windows reader fixture must demonstrate that a persistent lock fails, bytes remain intact, and release permits the move; it also checks removal and nontransient errors. Thus the bounded policy cannot silently count a persistently busy runtime as released.

The audit additionally found that stderr-read errors or callback unwinding could detach an output reader thread. `OutputReaders` now owns both joins, with drop order ensuring the child is killed/waited before remaining readers join. This robustness repair is separate from the reproduced rename failure; no read error or callback panic occurred in the captured failures.

Temporary native owner enumeration, handle duplication, Restart Manager and external Handle.exe instrumentation have been removed from the current code. The remaining optional feature records only process lifecycle and bounded-operation recovery counts. It is off by default, introduces no library/runtime dependencies and contains no production unsafe code. The stress workflow prints sanitized evidence only and uploads no artifacts. Qualification and publication remain blocked pending the corrected Windows stress run and complete native release matrix.

The first corrected stress batch also reported a late failure after all 55 child processes had completed. Its initial sanitized report did not retain the panic location, so a follow-up records only the source line and numeric OS error. Audit found the restored final runtime was still being deleted implicitly by TempDir rather than through the new host removal API. The test now explicitly removes that restored runtime through `remove_runtime_directory`, asserts its absence, and retains the independent `root.close()` assertion for all remaining temporary resources. This completes the intended removal coverage; the late error is not treated as explained until its safe diagnostic is available.
